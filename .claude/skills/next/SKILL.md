# /next — 你在哪、接下來做什麼

> 本檔為交付副本（自足）；正本住 ai-yorozuya `jarvis/skills/next/`，改正本→同步這裡。

這個專案照五站走：**意圖（含原型）→ 架構 → 規格 → 施工 → 回頭挑下一個動作**。
每站有明確的產出與過關條件；本 skill 的工作是**看檔案判斷你在哪站**，然後帶你走那一站——不代替你做任何判斷。

## 第一步：判斷現在在哪站（照順序檢查，第一個成立的就是）

| 檢查 | 成立 → 你在 |
|---|---|
| `intents/意圖定稿.md` 和 `intents/架構圖.md` 都不存在 | **意圖站** |
| 意圖定稿存在，架構圖不存在（或檔頭沒有「✅ 已簽核」） | **架構站** |
| 架構圖已簽核，但要蓋的動作在 `intents/` 沒有規格書 | **規格站** |
| 規格書存在，code 還沒蓋完或測試沒全綠 | **施工站** |
| 這個動作蓋完、驗收過 | 回架構圖挑下一個動作；全部夠用了→上線（`infra/`） |

**出廠範例分岔**：這個 repo 自帶「報價成交切片」的架構圖與規格書（已簽核的範例正本）。第一次打 `/next` 先問一題：

> 照範例蓋報價單系統，還是換成你自己的生意？

- **照範例** → 直接進施工站（範例的架構圖與規格書就是正本）。
- **自己的生意** → 先執行 `cp -r intents intents_範例參考`（範例留著隨時對照），再從意圖站開始。

## 各站怎麼走

### 意圖站
打 `/converge-intent`。兩個迴圈（意圖迴圈 ⇄ 原型迴圈）、兩道閘門，最後把**意圖定稿**寫進 `intents/意圖定稿.md`——五件：意圖清單／主流程（含主流程圖）／核心物件清單／暫不實作／待回答。

### 架構站
拿意圖定稿長成一張架構圖——**照範例架構圖的形**：四問／模組／流程／資料／頁面／原則／現在不做，七段、一頁（模組緊跟四問——先看邊界，再看細節）。**產出＝`intents/架構圖.md` 正本＋重生 `intents/系統總覽.html`**（整條知識層一頁：意圖定稿／知識架構圖／功能規格書三 tab＋五站進度帶，`gen-系統總覽.py` 派生——頁面從意圖站就出生、空的站顯示 ⏳ 跟著長大；md 一改**同 commit 重跑 gen**）。

**內容紀律・寫什麼（薄度）**

- 只寫 **AI 猜不到的判斷**——CRUD、分頁、按鈕長怎樣不寫；這份變厚就是警訊。為什麼用行內一句話帶（「金額不存總額欄位」式）。
- **不另立決策清單、不另立版本紀錄**——整份架構圖就是決策清單；版本紀錄＝git（翻案的為什麼寫進 commit message），正文永遠現在式（貼註記＝膠帶）。
- **深度判準**：被兩本以上規格書引用的住架構圖；只有一本在乎的住規格書（欄位、驗證、逐步操作、計算、單動作權限）。通用不變量住〈原則〉；**哪個角色能按哪顆鈕＝規格書〈權限〉段**。
- **user story 不另寫**（主流程每步已是「他做什麼／他看到什麼」的 story 形，再寫 As a… 是換行話重講）；**泳道圖單角色群不畫**（泳道價值在多角色交棒；真長出多角色再加）。

**內容紀律・怎麼切（模組與動作）**

- **模組照物件群切**：主單據＋它的明細與附屬紀錄＝一個模組（lean-stack 例：客戶／商品／報價單／訂單），邊界對齊 code 的 app／資料表分群（top-erp 慣例），不照技術層切（前端模組、API 模組＝錯）。切法是簽核物：起草時 AI 提案、簽核時人改。
- **橫切物件也要有家**：稽核／紀錄類物件自成支援模組（各模組寫入、它持有），不塞在某單據模組的附註（判例：修改紀錄）。
- **有「誰」就有使用者**：任何原則以「誰」開頭（誰改的、誰能按），使用者就是物件、身分就是模組；識別方式（挑名字／帳密）才是待拍的題。
- **規格書照動作切、順序照主流程挑**：一本規格書＝一個**可獨立驗收的動作**（做完能走一遍、看得到結果；切點優先落在狀態變化處；一本講不完＝再切）；一個模組多本規格書。「回頭挑下一個動作」看模組表。

**內容紀律・形與詞**

- **段落有形＝表格**：資料／頁面／原則／模組四段一律表格（流程段＝兩張圖）；**表格外不留散 bullet**——散條＝還沒分類，收進格子或刪（判例：資料段四條散 bullet，三條是物件定義、一條跟原則重複）。原則表固定三欄：「原則／守什麼／如何守住」；保護方式可連到測試、資料庫限制、權限檢查、操作紀錄或監測，未完成＝⏳。
- **〈流程〉段兩張圖**：**主流程圖**（他走的路，flowchart）＋**狀態機**（狀態與退路）——只畫狀態機＝使用者沒看過全貌（判例：lean-stack 報價單）。
- **〈模組〉段＝模組×頁面圖＋對照表**：圖＝模組為框、框內列頁面、跨模組流程與帶入各一條邊，橫切支援收**虛線框**、不畫連線網；對照表每模組一行（**模組｜資料｜重要流程（CRUD 一詞帶過不展開）｜守哪些原則｜規格書含狀態**）——資料、流程、原則的定義住各自段落，這張表只對照引用、不重複定義；跨模組流程（如轉單）住〈流程〉段的圖，模組表兩邊都列。
- **一物一名**：狀態與物件在圖、表、頁面、原型全用同一正名（正本＝〈資料〉段與狀態機）；口語同義詞不上正本（判例：「在談」＝已送出），方法內部詞（寄生、袋、卡、錨）也不上——寫人話（顯示於、附在）。

**起草（AI 做）**

1. 先問完意圖定稿「待回答」的欠帳題（表單，一題一題）。
2. 照形起草 md、重生 HTML。
3. 跑下面的**起草自檢**，逐條過了才開簽核表單——**不准帶病送簽**。

**起草自檢（送簽前逐條過；哪條不過就回去補，不是往下走）**

1. **五件都接住**：意圖清單→〈四問〉；主流程→〈流程〉；核心物件清單→〈資料〉每物件一列；暫不實作→〈現在不做〉；待回答→已問完、答案落進對應段。
2. **物件×頁面**：〈資料〉每個物件在〈頁面〉找得到家——自己的頁，或寄生（要寫宿主在哪）。
3. **狀態×退路**：狀態機每個前進邊都有退路，或明寫「不能退＋動作前確認框」。
4. **原則可判定**：每條原則都判得出成立或違反；「絕不能發生」每一條都有原則接住。架構站先定義承諾，不在這一站強迫指定唯一測試形式。
5. **模組覆蓋**：每個物件屬於一個模組、主流程每一步落在某模組的流程欄；模組表引用的資料與原則在〈資料〉〈原則〉段都找得到，無懸空引用。
6. **薄度與形**：沒有欄位型別、驗證、按鈕、單動作權限等規格細節混進來；四段都是表格、表格外沒有散 bullet。
7. **圖**：兩張圖照〈圖的紀律〉正本（[diagramming](../diagramming/SKILL.md)）、過出手前品質閘（語法 parse＋自己看過渲染結果）；HTML 已重生。

**簽核（人做，判斷永遠是人的；形＝差異簽核，不逐段細問）**

- **簽的是增量判斷，不是全文**：AI 列出「這張圖比意圖定稿多出的判斷」（模組切法、退路預設、AI 補的原則與歸屬……通常 2–5 條），逐條出拍板題附代價；其餘段落＝意圖定稿的投影——投影保真由起草自檢擔保，**不逐段出題**（判例 2026-08-23：七段逐段勾、四題有三題答案可預測全「都對」——可預測＝零資訊，nolan 拍板「連架構圖都不太需要細問」。這是框架 §5.8 P8 分層簽核在正向路徑的落地）。
- **看過的證據＝至少一個真決定**——增量判斷題本身就是；增量全空（整張純投影）才追問一次「哪一句讀起來怪怪的？改它」。不出「請挑一處改」的儀式題——為改而改＝假修改（判例：被打回「問這個有何意義」）。真疑點照 asking 當真題、在該問的站問。
- HTML 照開在他眼前，任何一段他隨時可指著改；簽核＝檔頭補一行 `> 狀態：✅ 已簽核 YYYY-MM-DD（真決定：…）`。

**之後長新流程（連動＝單向生長）**

1. **新流程先過圖**：主流程圖加邊、狀態機加狀態、資料段加物件、原則段加不變量——改完跑一次起草自檢，**只簽 diff 那幾段**，不整張重簽。
2. **規格書掛錨、圖掛狀態**：規格書檔頭寫「模組：〈模組名〉／動作：〈動作名〉」；架構圖模組表那行掛回連結＋狀態。
3. **共用判斷只住架構圖**（狀態機、原則、物件關係），規格書**引用不抄寫**——抄一份就是第二正本，漂移從那開始。反向唯一合法動作：施工發現圖錯 → 回去改圖、重簽那段，再回來施工。

### 規格站
**簽圖後批次起草全部動作的規格書、人一次 review 完**（nolan 拍板 2026-08-23：召喚人 N 次各審一本＝浪費他的注意力；共用判斷已凍結在架構圖、規格書薄，批次成本低）。**照範例規格書（建立報價單.md）的形**：這個動作在做什麼／欄位／計算／權限／驗收；檔頭固定兩行＝錨＋「只講『X』這一個動作。狀態、原則、資料的定義都在知識架構圖——這裡引用、不重抄。」**欄位用樣張呈現，不另立欄位表**：單據類動作＝一張填好假資料的單，規則直接標在單上（〔〕＝規則、＊＝必填）；列表類＝一小段排好序的假列表——讀規格的人看到的就是他以後會看到的東西（nolan 拍板 2026-08-23「直接呈現一張單」；宗旨＝規格對應實作、看得懂、驗得動）。**已施工的動作補〈對應實作〉段**（API／測試檔／畫面狀態）——規格跟系統的對應要指得到。**規格書寫人話**：方法話術（「切一塊放大」「長出來」「兌現」「落地」「最薄能動」「一物一名」…）不進交付文件——方法的為什麼住 skill 與正本，文件只寫規則本身（判例 2026-08-23：六本規格書滿版行話，被打回「很多很怪的用詞」；同判例：內部詞不上桌本是對話規則，交付文件同樣適用）。Review 照差異簽核精神：每本只亮它的**判斷點**（AI 預設＋代價），全套一場拍完。**Review 載體＝`intents/系統總覽.html` 的規格書 tab**（子 tab **照模組分群**——模組管邊界的層級要看得見，平鋪六本＝散裝；判斷點置頂；`gen-系統總覽.py` 從各本 md 重生——md 是正本，改了 md 同 commit 重跑）。

**施工前每本必跑校對 pass**（庫存保鮮機制）：對齊最新架構圖＋吸收前面施工的學習（判例：建立報價單出廠帶「端點公開」，使原則 3 無法判定與保護；施工前校對一輪修正——批次庫存會漂，校對把漂移吸掉，這是批次切的配套、不可省）。

**出規格書前自檢（四條）**：①錨掛好、模組表那行已回鏈②共用判斷（狀態機、原則、物件關係）只引用不抄寫③**取捨不得讓原則失去判定或保護方式**；會的話先回架構圖改（改原則或掛 🔴）再出規格書④〈驗收〉每一條都寫成可操作、可觀察結果，不用「正常」「正確」「完成」等無法直接判定的字眼帶過。

- 檔頭第一行掛錨：「模組：〈模組名〉／動作：〈動作名〉」。
- 第一刀怎麼挑：主流程上**最靠近錢的那個動作**。
- 規格從架構圖長出來，不從畫面長出來。
- 一個動作一份檔，存 `intents/<動作名>.md`。

### 施工站
對 AI 下單用固定句型：**做哪個動作＋規格在哪＋原則照 `intents/架構圖.md`〈原則〉＋怎麼驗**（例：「做建立報價單，規格照 intents/建立報價單.md，原則照架構圖，驗收跑它的驗收段」）——共用判斷住架構圖、規格書只引用，下單不帶架構圖＝AI 拿不到原則。紀律：

1. **plan-first**——先看施工計畫、找碴，再動手。
2. **一次一個小增量**，做完能跑再繼續。
3. **替原則加上保護方式**——架構圖每條重要原則至少要有一種可執行的保護方式；依風險選測試、資料庫限制、權限檢查、操作紀錄或監測，必要時多層並用，並把位置回填架構圖〈如何守住〉欄。計算不變量可優先用 property-based 測試，狀態流轉用例測，唯一性與引用完整性通常也要靠資料庫限制。
4. 改壞就退回（git），敢改的底氣是隨時退得回。

**驗收＝三件都過**：規格書驗收段逐條過（本次功能）＋架構圖的重要原則已有保護方式且檢查通過（跨功能底線）＋照主流程把畫面從頭走一遍（端到端工作流程）。
**升格迴路**：驗收撞到的問題，一次性的當場改；會再犯的**升格**成原則測試或驗收段一條（先改正本再施工）——文件只長被咬過的地方。

### 完成一個動作之後
回架構圖：挑下一個動作出規格書；或「現在不做」清單裡有東西真的痛了→**先改圖，再施工**。要給別人用了→上線（`infra/`，照 `infra/README`）。

## 圖的紀律（任何要給人看的圖適用）

正本＝[diagramming](../diagramming/SKILL.md)——動筆前三問／兩個場景配色／怎麼畫（mermaid）／出手前品質閘（語法 parse 必過＋渲染結果自己看過，各至多 2 輪）。本 skill 的圖屬**人面收斂場景**（2–3 色編類別：紫＝主單據流程、綠＝下游單據、灰＝旁支／橫切；橫切支援框用虛線示意容器）。就地硬線兩條：

- **全貌先行**：流程先有一張整條的圖，局部簽核錨在圖上；只給表格或文字箭頭＝沒交。
- **圖是派生、文字是正本**：改流程先改文字行，圖跟著重畫；圖文不符以文字為準。

## 紅線

- **判斷是人的**：架構圖與規格書的每個決定都要人點頭；AI 只出草稿與選項（附代價）。
- **不跳站**：沒簽架構圖不出規格書，沒規格書不施工。
- **新需求不直接改 code**：先問它長在架構圖哪裡（新的東西？新狀態？撞到哪條原則？），改完圖再切一個動作施工。

## 回報格式

每次 `/next` 開場先報三行，再開始帶站：

```
你在：施工站（建立報價單）
上一站交付：intents/建立報價單.md ✅
這一站目標：後端 API 蓋好、原則 1/5 的測試綠
```
